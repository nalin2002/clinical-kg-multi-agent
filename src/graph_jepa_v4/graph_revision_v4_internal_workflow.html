Graph-JEPA v4 Internal Workflow

This document explains the v4 clinical KG revision pipeline from graph loading through schema sanitization, masked pretraining, joint fine-tuning, schema-aware edge revision, scoring, candidate generation, and pruning.

1. Goal

v4 keeps the v3 revision question:

Should this typed edge exist in this specific patient graph?

The difference is how the model is trained and how schema mistakes are handled. v4 first learns graph patch representations without the edge revision objective. Then it fine-tunes with both representation and revision losses while treating schema-invalid observed edges as negatives. 

pretrain_loss = jepa_weight * patch_jepa_loss

finetune_loss = jepa_weight * patch_jepa_loss
              + revision_weight * schema_aware_revision_loss

2. Inputs and Setup

v4 uses the same patient KG JSON contract as the earlier Graph-JEPA versions. It can train from synthetic graphs, MIMIC graphs, MIMIC sub-KGs, or ACI-Bench KGs.

Data option Builder Typical source
synthetic SyntheticGraphGenerator Generated toy graphs for smoke tests.
mimic MimicGraphBuilder MIMIC source tables and optional notes.
mimic-subkgs MimicSubKGGraphBuilder JSON sub-KGs such as outputs/graphs_multi_agent/sub_kgs.
aci-bench AciBenchGraphBuilder Cooperative multi-agent ACI-Bench output KGs.

The saved checkpoints are deliberately separated: 

graph_jepa_v4_pretrain.pt  # masked pretraining checkpoint
graph_jepa_v4.pt           # final joint fine-tuned checkpoint

3. Graph Preprocessing

Tensor conversion is inherited from v3 through src/graph_jepa_v4/data.py. Each node receives a typed text embedding and each valid relation name receives an integer edge type. 

{
  "nodes": [
    {"id": "N_006", "text": "shortness of breath", "type": "SYMPTOM"}
  ],
  "edges": [
    {"source_id": "N_006", "target_id": "N_001", "type": "INDICATES"}
  ]
}
Tensor Shape Meaning
x [num_nodes, encoder_dim] Embedding of each (node.type, node.text) pair.
node_type [num_nodes] Integer schema type for each node.
edge_index [2, num_edges] Source and target node indices.
edge_type [num_edges] Integer relation ID for each edge.

Schema masks

v4 adds a schema pass in src/graph_jepa_v4/model.py. For each observed edge, it compares the source node type, relation, and target node type against RELATION_SCHEMA. 

schema_valid, schema_invalid, unconstrained = _schema_edge_masks(data)
message_mask = schema_valid | unconstrained

Unconstrained relations such as ASSOCIATED_WITH and CO_OCCURS_WITH are allowed to remain in message passing. Typed-invalid edges are removed from message passing and later used as negative training examples.

4. Patch Creation

Patch construction is inherited from v3 through src/graph_jepa_v4/patches.py. v4 builds patches after schema sanitization, so masked pretraining sees a cleaner graph. 

message_data = sanitized_graph_data(data)
patch_data = build_patch_data(
    message_data,
    num_patches=8,
    patch_pe_dim=8,
)

The patcher uses balanced multi-source BFS: seed high-degree and far-apart nodes, grow local BFS regions, keep patch sizes roughly balanced, and assign leftover disconnected nodes to the smallest available patch.

Patch object Meaning
assignment Node-to-patch mapping.
patch_nodes Original node indices inside each patch.
patch_edge_index Coarsened patch graph edges.
patch_pos Patch size, degree, and random-walk style structural features.

5. Architecture

GraphJEPAv4 subclasses GraphJEPAv3. The node encoder, patch transformer, EMA target branch, predictor, and edge plausibility head are the same architecture. The v4 difference is in the training pipeline, schema-aware loss, and scoring guard.

1. Node encoder Typed-edge GNN turns node text embeddings into contextual node latents.
2. Patch pooling Node latents are mean-pooled into patch latents.
3. Patch transformer Context and target branches encode masked and unmasked patch structure.
4. Edge head Scores typed triples for keep, prune, add, or reject decisions.

The context branch receives masked patch content and learns by gradient. The target branch receives the full graph and is updated by exponential moving average: 

target_weights = decay * target_weights
               + (1 - decay) * context_weights

6. Stage 1 Pretraining

The first stage runs graph_jepa_v4.pretrain. It trains only the masked patch prediction objective. 

use_revision = False
loss = jepa_weight * patch_jepa_loss

In each batch:

  1. Load a PyG batch of patient graphs.
  2. Remove typed-invalid edges from message passing with sanitized_graph_data.
  3. Build balanced BFS patches on the sanitized graph.
  4. Sample context and target patches.
  5. Predict EMA target patch representations from masked context representations.
  6. Update the online model by gradient and the target model by EMA.

The checkpoint stores the model weights and config in graph_jepa_v4_pretrain.pt plus config_v4_pretrain.json.

7. Stage 2 Fine-tuning

The second stage runs graph_jepa_v4.finetune. It loads the masked-pretrained checkpoint, preserves the recorded pretrain epoch count, and trains both losses together. 

model, cfg = load_model_checkpoint(pretrain_checkpoint)
cfg.train.finetune_epochs = args.epochs
cfg.train.epochs = cfg.train.pretrain_epochs + cfg.train.finetune_epochs

loss = jepa_weight * patch_jepa_loss
     + revision_weight * schema_aware_revision_loss

Fine-tuning still builds patches from sanitized message data, but the revision loss receives the original graph so observed schema-invalid edges can become negative examples.

8. Schema Revision Loss

v4 changes the edge-revision objective while keeping the same keep, prune, add, and reject semantics.

Positive examples

Only schema-valid observed typed edges are positives. Some of those positives are hidden from message passing with revision_mask_ratio so the model learns missing-edge recovery. 

pos_mask = schema_valid
hidden[pos_idx] = random_mask(probability=revision_mask_ratio)
keep = message_mask & ~hidden

Negative examples

Negative source How it is created What it teaches
Schema-valid absent triples Sampled from the same graph using v3 hard-negative logic. Do not add plausible but unsupported edges.
Observed schema-invalid triples Already present in the input KG but incompatible with RELATION_SCHEMA. Do not learn extractor artifacts as truth.
Reversed invalid triples Reverse valid positives when the reversed relation would violate the schema. Respect edge direction.

Relation-balanced BCE

v4 computes binary cross entropy per example, then averages by relation and label cells. This prevents frequent relation types from washing out rare relation mistakes. 

for relation in unique(relations):
    for label in [0, 1]:
        cell_loss = mean(bce[relation == rel and labels == label])
    relation_loss = mean(cell_losses)

revision_loss = mean(relation_losses)

The training logs expose revision_invalid_neg, revision_reverse_neg, revision_hidden, and schema_dropped_edges, which are useful for checking that the schema-aware path is active.

9. Inference

Existing edge scoring

v4 calls the v3 scorer, then applies a schema guard. The base score still combines the edge head probability with a patch structural score: 

p_head = sigmoid(edge_head(z_source, z_target, relation))
structural = exp(-patch_prediction_energy / energy_temperature)
score = alpha * p_head + (1 - alpha) * structural

The default alpha is 0.9, so the edge head dominates while patch energy remains a small structural signal.

Schema guard

After scoring, each edge is checked against RELATION_SCHEMA. Invalid typed edges are annotated and forced into the inconsistent band. 

if edge_schema_error(edge):
    edge["jepa_schema_valid"] = False
    edge["jepa_schema_error"] = error
    score = min(score, schema_invalid_score)
    flag = "inconsistent"
else:
    edge["jepa_schema_valid"] = True

Candidate addition

Candidate generation reuses the v3 candidate iterator and then writes v4 metadata for accepted additions: 

{
  "jepa_suggested": true,
  "jepa_unverified": true,
  "jepa_source": "graph_jepa_v4_candidate_generation",
  "jepa_schema_valid": true
}

Relation-specific thresholds are stricter for many MIMIC-style relations, such as DIAGNOSED_BY, INVESTIGATED_BY, and PERFORMED_FOR. This keeps candidate additions conservative.

10. Commands

Pretrain on ACI-Bench KGs

PYTHONPATH=src python -m graph_jepa_v4.pretrain \
  --data aci-bench \
  --aci-kg-path outputs/aci_bench/sub_kgs \
  --out ckpts \
  --encoder mock \
  --gnn-backend pyg \
  --epochs 50

Fine-tune from the pretrain checkpoint

PYTHONPATH=src python -m graph_jepa_v4.finetune \
  --data aci-bench \
  --aci-kg-path outputs/aci_bench/sub_kgs \
  --checkpoint ckpts/graph_jepa_v4_pretrain.pt \
  --out ckpts \
  --epochs 50 \
  --revision-weight 1.0 \
  --revision-mask-ratio 0.25 \
  --revision-neg-per-pos 3

Score a directory of KGs

PYTHONPATH=src python -m graph_jepa_v4.score \
  --input outputs/aci_bench_val/sub_kgs \
  --checkpoint ckpts/graph_jepa_v4.pt \
  --output outputs/aci_bench_val/v4_scored \
  --add-candidates \
  --max-candidates 50

Use v4 in the end-to-end wrapper

GRAPH_JEPA_MODULE=graph_jepa_v4 \
GRAPH_JEPA_CKPT=ckpts/graph_jepa_v4.pt \
./run_aci_bench.sh

11. Improvements over v3

Problem in v3 v4 change Effect
Representation learning and revision learning started together. Masked pretraining runs first; revision fine-tuning starts from that checkpoint. Patch representations get a cleaner warm start before edge decisions dominate training.
All observed edges were effectively positive training signal. Only schema-valid typed observed edges are positive. Extractor or adapter artifacts are less likely to be reinforced.
Invalid observed edges could still participate in message passing. sanitized_graph_data removes typed-invalid edges from message passing. Bad edge directions do not contaminate node and patch latents.
Hard negatives were mostly schema-valid absent triples. v4 adds observed-invalid and reversed-invalid negatives. The model learns both plausibility and clinical schema direction.
Frequent relations could dominate the edge loss. Relation-balanced BCE averages by relation and label cell. Rare relation mistakes receive a clearer learning signal.
High model scores could override type-schema impossibility. The scoring guard caps invalid edges and records jepa_schema_error. Outputs are easier to audit and safer for downstream review.

12. Limits

  • Schema validity is not the same as clinical correctness.
  • Candidate additions still carry empty evidence and must remain unverified.
  • The schema guard depends on node typing quality in the input KG.
  • Training quality still depends on source KG coverage and extractor consistency.
